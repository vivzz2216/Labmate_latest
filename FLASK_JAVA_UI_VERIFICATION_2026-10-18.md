# Flask and Java UI verification

Flask, AWT and Swing now have dedicated runtime adapters in the normal assignment workflow. The structured generation response includes complete project files and bounded declarative interaction tests in the same call. No model-authored executable test scripts are accepted. Original task numbers, source files, requirement coverage, test observations and failure status remain preserved.

## Execution and evidence

- Flask runs a temporary loopback WSGI application with real templates, static files, GET/POST routes and server validation. Debugging and reloading are disabled. The browser uses the existing origin restriction, CSP and bounded interaction runner. Flask imports are permitted only for an explicitly validated Flask project. Paths, file-serving helpers and template introspection are restricted.
- AWT/Swing source and the trusted host compile with the configured JDK. Every scenario starts a fresh JVM. On Windows, the application runs on a new inactive desktop; the host never switches desktops or reads the user's screen. Linux uses `xvfb-run` and refuses to attach an existing display as a fallback.
- Java tests fill real controls, dispatch actual handlers, select values and assert visible component state. Modal dialogs are exercised. A constant result already present before clicking does not prove the requested calculation. Screenshots are actual Java component prints, excluding native window chrome; they are not HTML reconstructions or OS screen grabs.
- A wrong result, missing handler/control, hung handler, failed compile, missing display or absent test plan cannot become verified. Diagnostic Word reports remain downloadable. The existing controlled-beta execution gate remains required; private displays are not an untrusted-code VM.
- JavaFX and Tkinter remain unsupported. This release does not add database experiment verification or extra Python packages beyond Flask.
